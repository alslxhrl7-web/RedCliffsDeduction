# 수정기록

패치노트(PATCH_NOTES.md)와 별도로, 발견된 문제가 어떻게 고쳐졌는지 기록하는 문서입니다.
각 항목은 발견 내용, 현재 상태, 수정 내용, 검증 결과를 함께 남깁니다. 수정 후에는 상태와 수정 내용을 갱신합니다.

상태 표기: 미수정 / 수정 중 / 수정 완료 / 보류

## 2026-10-10 발견 문제

### 1. 오브젝트에 다가가면 확인 안내("E · …")가 켜졌다 꺼졌다 함
- 발견: 사용자 보고. Unity 플레이 모드에서 재현함. 모든 상호작용 대상(19개) 앞에서 걸어 다가가며 매 0.02m마다 `FindTarget()` 결과를 기록. 912번 걷기 중 27번에서 안내가 여러 번 켜졌다 꺼짐(수군 배치도 탁자 10, 발급 담당 기록 탁자 11, 문서고 이동 표지 4, 수송 물품 상자 2). 예: 수군 배치도 `T@3.36 > - @3.18 > T@3.16 > - @3.14 > T@3.12 …`처럼 거리 3.0~3.4m에서 2~4cm마다 반복.
- 원인: 안내는 `FirstPersonInvestigator.Update`가 매 프레임 `FindTarget()` 결과로 바로 쓰고 지움. `FindTarget()`은 정면 레이(3m)와 구 스윕(반지름 0.1m + 보이는지 확인)의 두 단계인데, 상호작용 거리 경계(3m)에서 두 단계의 기준이 달라 결과가 프레임마다 바뀜. 시선이 대상 모서리나 붙어 있는 다른 대상 경계에 걸려도 결과가 바뀜.
- 관련 코드: `FirstPersonInvestigator.Update`, `FindTarget`.
- 상태: 수정 완료(Unity 플레이 모드 재현·검증). 일부는 의도된 동작이라 남김.
- 수정 내용 (2026-10-10): 이미 잡은 대상은 범위(+0.35m)와 시선 여유(구 반지름 0.15m)를 더 줘서 유지(`FindTarget(current)`, `StillAimingAt`). 십자선이 다른 대상을 정확히 맞히면 바로 그쪽으로 바뀜. 순간적으로 대상을 놓쳐도 0.12초는 안내를 유지(`PromptGrace`). 인자 없는 `FindTarget()`은 그대로라 범위 밖·벽 너머는 여전히 `null`.
- 검증: 같은 걷기 재현 27건 → 2건. 남은 2건은 수송 상자 앞을 기록 탁자가 정확히 가리는 경우로 의도된 전환. `군령 조사 검사` PASS 56 / `failures=0`, 콘솔 오류 없음. 컴파일 검사 통과.
- 남은 점(의도된 동작): 손을 떨 때 서류 목패 ↔ 서류함 뚜껑, 수송 상자 ↔ 기록 탁자처럼 십자선이 실제로 서로 다른 물체 사이를 오가면 안내가 그 물체로 바뀜. 문은 십자선이 옆 벽에 닿으면 벽이 가려서 꺼짐. 실제 플레이 화면에서 눈으로 확인한 것은 아님.

## 2026-10-09 발견 문제

### 1. 최종 보고 문구와 판정이 어긋남
- 발견: 근거 6개를 모두 제출했지만 조치를 틀리면 NORMAL이 나오는데, 엔딩 문구와 조조의 명령 문구는 "근거가 갖춰지지 않았다"고 표시함.
- 관련 코드: `OrderFinalReport.Resolve`, `InvestigationSession.OrderFinal.cs`의 `CompleteOrderFinal`, `ShowOrderEnding`.
- 상태: 수정 완료(코드 적용, Unity 실행 검증 전)
- 수정 내용 (2026-10-09): 결말 문구를 선택한 조치별로 나눔. 근거 6개를 모두 냈는데 조치가 틀린 경우 "근거가 부족하다" 대신 "보고는 확인했다. 그러나 제17호를 멈추라는 명령은 내리지 않는다"로 표시(`OrderCommandText`, `NormalEndingDetail`). `OrderFinalReport.EvidenceComplete` 추가.
- 검증: `OrderFinalChecks`에 "근거 완비 · 조치 없음" 문구 검사를 추가함. Unity 실행은 아직 안 함.

### 2. 조치 3번 함정이 "조치 없음"과 같은 결말로 처리됨
- 발견: "회수본대로 본진 철수를 요청"을 고르면 "별도 시행 조치를 요청하지 않는다"와 같은 NORMAL 문구가 나옴.
- 관련 코드: `OrderActions`, `OrderFinalReport.HoldsOrder`, `RestoresDeployment`.
- 상태: 문구 수정 완료(실행 검증 전). 결말 등급은 보류.
- 수정 내용 (2026-10-09): 조치 3의 명령 문구와 결말 문구를 따로 만듦("회수본대로 철수 명령이 시행됐다. 강 입구의 감시선이 빠져 접근하는 선단을 놓칠 위험이 커졌다"). 결말 등급(NORMAL)은 유지.
- 남은 결정: BAD로 올릴지는 `최종 보고 구성.md` 기준과 맞춰 정해야 함.
- 검증: 조치 3 결과가 NORMAL인지 기존 검사가 확인함. 문구 차이는 실행 화면에서 확인해야 함.

### 3. 최종 보고의 근거 선택이 정답 체크리스트처럼 보임
- 발견: 확보하지 않은 근거도 이름이 전부 보이고, 6개를 모두 고르면 TRUE가 되어 "전부 선택"이 정답 구조가 됨. 틀린 근거 선택지가 없음.
- 관련 코드: `OrderFinalReport.Available`, `ShowOrderFinalProofs`.
- 상태: 수정 완료(코드 적용, 실행 검증 전)
- 수정 내용 (2026-10-09): 확보하지 않은 근거의 이름을 "아직 찾지 못한 근거"로 숨김. 근거 목록을 페이지당 3개씩 3쪽으로 나눔. 7번째 근거 "문서실 출입 기록과 한진의 취급 권한"을 미끼로 추가(`OrderReportProof.AccessRecord`, 비트 64, 발송 사실을 알면 선택 가능). 미끼를 같이 제출하면 TRUE가 되지 않음. 정답 근거 집합(63)은 그대로.
- 검증: `OrderFinalChecks`의 행렬 검사를 0..127로 넓히고 미끼 포함 시 NORMAL 검사를 추가함. 샌드박스에서 `OrderFinalReport`만 따로 컴파일해 전 조합(7×128×4)을 돌린 결과, TRUE는 (한진, 63, 조치1) 한 조합뿐이고 미끼 포함 시 NORMAL, 미끼만 제출 시 BAD였음.

### 4. 수첩 세 질문 추리의 선택지가 정답을 미리 드러냄
- 발견: 변경 시점, 제출자, 고의 판단 모두 선택지가 2개뿐이고, 정답 선택지가 증거 확보 전에도 회색으로 보임. 오답도 허수아비 논리이고 틀려도 대가가 없음.
- 관련 코드: `InvestigationSession.OrderFollowUp.cs`의 `ShowOrderSubmission`, `ShowOrderReplyOrder`, `JudgeFollowUp`.
- 상태: 수정 완료(코드 적용, 실행 검증 전). 오답의 대가는 보류.
- 수정 내용 (2026-10-09): 정답 선택지를 회색 대신 "증거 확보 후 등장"으로 바꿈.
- 수정 내용 (2026-10-10): 질문마다 정답 1개와 그럴듯한 오답 2개를 항상 함께 보여 줌. 오답은 사실 하나를 근거로 들지만 기록 하나를 빠뜨린 문장이라, 무엇을 놓쳤는지 생각하지 않으면 구분되지 않음. 정답 위치도 질문마다 다름(2번째·3번째·1번째). 증거가 모이기 전에는 세 선택지 모두 같은 중립 문구("지금 수첩에 있는 자료만으로는 이 판단을 확정할 수 없다")를 돌려줘서, 버튼이 켜지는지로 정답을 알 수 없음. 증거가 모인 뒤 오답을 고르면 정답을 말하지 않고 다시 볼 기록만 짚어 줌.
  - 1번(변경 시점): 정답 "전달자가 받기 전에 바뀌었다 · 넘기기 전 기록부터 이미 철수다". 오답 "전달자가 받은 뒤 바뀌었다 · 그가 묶음을 따로 숨겨 두었다"(숨긴 것은 사실, 출고 기록을 놓침). 오답 "처음부터 철수였다 · 한진은 받은 대로 옮겨 적었다"(의뢰서 문구를 따옴, 반환된 원문·확인표를 놓침).
  - 2번(제출자): 오답 "제출자는 한진 · 의뢰서에 재작성 담당으로 적혀 있다"(결론은 같지만 근거가 담당 배정뿐). 오답 "단정할 수 없다 · 접수 뒤 출고 사이에 바뀌었을 수 있다"(접수 때 이미 철수였다는 기록을 놓침). 정답 "제출자는 한진 · 그가 반납한 완성물이 그대로 출고됐다".
  - 3번(고의): 정답 "알고 제출했다 · 답신을 직접 받은 뒤에 철수 본문을 냈다". 오답 "알고 제출했다 · 거절 회신이 나간 뒤에 철수 본문이 들어왔다"(발송과 수령을 혼동). 오답 "착오였다 · 회신의 '재작성 진행'을 수정 허가로 읽었다"(회신의 '내용 보존'과 '강 입구 유지를 바꾸지 않는다'를 놓침).
- 검증: `OrderFollowUpChecks`의 클릭 문자열을 상수(`InvestigationSession.Judge…`)로 바꾸고, 새 오답 각각이 기록을 바꾸지 않는지, 증거 전에는 세 선택지가 모두 같은 반응을 보이는지 검사를 추가함. Unity 실행은 아직 안 함.

### 6. 한진 자백 대사가 증거 없이 자동으로 바뀜
- 발견: 세 번째 판단을 마치면 한진의 해명 대사가 자동으로 "변경하지 말라는 답신을 받고도 내 판단대로 철수 본문을 넘겼소"로 바뀜. 증거를 제시해 자백을 끌어내는 장면이 없음.
- 관련 코드: `InvestigationSession.OrderFollowUp.cs`의 `ShowOrderHan`.

- 수정 내용 (2026-10-09): 한진의 첫 대사는 판단 기록과 무관하게 고정. 해명을 들으면 부인하는 대사만 나옴. 고의 판단과 수령 기록이 있을 때 "거절 답신의 수령 기록을 들이민다" 선택지가 생기고, 이것을 골라야 자백 대사가 나옴.

## 남은 항목

- 조치 3을 BAD로 올릴지 결정 필요.
- 세 질문에서 오답을 골라도 대가 없이 "다시 판단"할 수 있어, 세 개를 차례로 눌러 보는 방식은 여전히 가능함.
- 본편 조사(`InvestigationSession.Orders.cs`)의 "전달자가 군령을 조작했다", "접근 권한이 있는 사람을 범인으로 확정" 같은 판단 선택지도 같은 허수아비 형태로 남아 있음(이번 범위 밖).
- 3번 질문 화면은 선택지가 4개에서 5개로 늘어 본문 영역이 줄었음. "스크롤 없이 요약이 보이는가" 검사가 통과하는지 실행으로 확인해야 함.

## 검증 기록

- 2026-10-10: 수정한 C# 파일 5개를 Mono `mcs --parse`로 문법 검사해 오류 없음. `OrderFinalReport`·`OrderInvestigationState`만 따로 컴파일해 결말 판정 행렬을 실행해 확인함.
- 2026-10-10 (버그 검사 이어서): 이 컴퓨터의 Unity 6000.6.0f1 엔진 참조 파일과 프로젝트의 패키지 어셈블리(Input System, UI, URP 등)를 써서 Unity 밖에서 프로젝트 스크립트 전체(런타임 27개+, 에디터 40개+)를 실제로 컴파일함. 결과는 다음 세 가지 모두 오류 0개, 수정한 파일 경고 0개.
  - 게임 빌드용 런타임 스크립트 (UNITY_EDITOR 없이)
  - 에디터용 런타임 스크립트
  - 에디터 스크립트와 검사 코드 (`OrderFinalChecks`, `OrderFollowUpChecks`, 새 `PlaytestObserverChecks` 포함)
- 2026-10-10: 6개 수정과 관련된 다른 코드 경로를 확인함. 저장 파일 검증(`InvestigationSaveData.Validate`)은 `OrderFinalReport.Validate`를 그대로 사용해 미끼 근거(비트 64)가 들어간 저장도 정상으로 읽힘. 근거 범위를 따로 63으로 막는 다른 코드는 없음.
- 아직 하지 않은 것: Unity 플레이 모드에서 `적벽추리/군령 조사/진행과 저장 검사` 실행, 빌드, GitHub 업로드. 컴파일 통과는 실행 결과(화면 크기, 클릭 흐름)까지 보장하지 않음.
